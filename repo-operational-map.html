CYBERCROWD REPO OPERATIONAL MAP V1
Operational repository authority map for CyberCrowd. This document defines what belongs in GitHub, what belongs in Pages, what belongs in R2, and what must remain separated.
REPO-001
Core Rule
The repository is not the platform. The repository defines: structure logic routing surfaces authority rules deployment law The repository does not hold: live canon replay truth quarantine payloads heartbeat streams public intake overflow

REPO-006
Pages Authority Discovery
Critical discovery: Cloudflare Pages owns deployment regeneration. Generated Workers are runtime artifacts. Persistent bindings belong in: Pages Functions bindings Not: Workers settings API This became a foundational operational rule.
REPO-007
Static vs Dynamic Separation
Static: repo Pages surfaces CSS frontend logic public assets Dynamic: R2 event streams heartbeat streams replay streams intake payloads continuity reconstruction Static surfaces should not become: operational truth storage.
REPO-008
Deployment Discipline
Deployment rules: - controlled commits - single-purpose mutations - verify after deployment - preserve binding state - avoid broad auto-write behavior - avoid uncontrolled optimization - freeze after successful mutation Pages regeneration is expected behavior.

REPO-010
Final Rule
CyberCrowd survives through: separation of authority. Repo defines structure. Pages deploys surfaces. R2 preserves operational continuity. Do not collapse these layers together.
